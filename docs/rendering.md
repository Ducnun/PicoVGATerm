# Rendering
Rendering is currently kept simple. The PIO block that generates the video signal just pulls data out of a block of memory called the framebuffer. To generate a certain image, we can manipulate this framebuffer directly. Currently, there is no synchronisation mechanism in place. This means that if a line is being output while the processor is rendering some glyph or sprite in that same place, tearing will happen where parts of the frame represent different moments in time. With simple rendering like bitmap look ups this problem is not too bad, but any heavier or global operations on the framebuffer will almost definitely result in tearing. 

## Characters
The first priority of this graphics processor is to be able to render a terminal. For a terminal, the rendering logic is not too complex. It mostly involves being able to render characters, preferably in different colours and some way to scroll up or down. 
Rendering characters is done with the help of a bitmap that represents a font. This is indexed based on ASCII values. To draw it, the ASCII value is used as an index in an array of bitmaps, returning a single glyph. This glyph uses 1 bit per pixel to represent whether this pixel should be the foreground or background colour. The rendering engine uses this bitmap and 2 provided colours to put a byte that represents the right colour into the right place in the framebuffer relative to the character position specified. These draw operations are inherently pretty cheap, especially compared to how many times a second a character needs to be drawn for a terminal to feel responsive.

## Scrolling
Again, the first priority is to render a terminal and so this next part mostly focusses on scrolling through a terminal. This same scroll mechanism is however what can be used to optimize scrolling through a background in a sidescroller game.
Scrolling a terminal can be done a few ways. The naive way is to redraw all the scrolled characters in the new position and to "render" an empty character. This however, requires the graphics processor to understand the framebuffer, which is undesired, and is extremely expensive. Instead, the entire framebuffer is moved. This means that any drawn graphics or glyphs can be reused rather than having to be redrawn. This memory operation can be optimized even further later on by having the DMA peripheral perform this move while the CPU renders the new line (whether it's a character or just emptying part of the framebuffer) in a temporary cache and then appends it to the framebuffer, but this introduces some risks if that temporary cache becomes too large. However, depending on DMA contention from the VGA signal output, it could still be beneficial to use a DMA channel to perform the move. This would free up the CPU to handle interrupts while the scroll can still be performed, even if the CPU would have to actively wait to render the new lines to prevent cache size issues. 

## Simple shapes
For now, the only shape implement is a simple filled rectangle. This is used when scrolling through the terminal. The reason this is needed is because the memory move done when scrolling wraps around the lines that are supposed to be moved off screen to where the new lines should appear. This rectangle fill can thus be used to clear that part of the framebuffer cheaply.
