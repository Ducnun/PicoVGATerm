# Pico GPU
The goal of this project is to implement a simple graphics processor based on the RP2350 microcontroller. It will be able to receive a set of instructions from an external source, render this into an image, and output this to a VGA output.

## Current Limitations
Due to the way that the programmable IO blocks in the microcontroller scale their clocks and the current reliance of 3 separate state machines, the pixel clock is currently not running at a perfect 25.175 MHz clock. Instead, to use integer clock division for the state machine without breaking the reliability of the PLL on the microcontroller, a pixel clock of 25MHz is set. Most displays will support this perfectly fine, but the introduction of upscalers or very strict displays might result in the video signal not being recognized.

Another limitation comes from the way that the programmable IO uses a byte to output to pins. It is preferrably to have 8 conesecutive pins (e.g. 2-9) for the 8 color pins. There are some pins on the RP2350 that are not necessarily reserved, but can show unexpected behaviour when trying to use them in state machiens. One example is pins 0 and 1 (default UART).

Since the current implementation uses a full framebuffer of 1 byte per pixel at a resolution of 640x480, a single framebuffer takes up about 60% meaning it is not possible to use double buffering to prevent tearing. Instead, in the future, an interrupt will be generated by the VSYNC state machine to mark what line is being output and thus not safe to write to.p

## Current Progress
The version found in the main branch as of right now contains a functional signal output that is mapped 1 to 1 to the framebuffer. It provides a way to render characters through the present bitmap fonts and a way to scroll through the buffer. It provides a simple lookup table for 16 colours that are mapped to the original Commodore 64 colours as best as possible with the current DAC setup. It currently contains some logic for a terminal, but this is misplaced for the final project as this logic should reside in the host, not the graphics processor.

## Next Steps
The next step is to provide an external communication interface, either through a simple UART connection or by leveraging a second PIO block to create an SPI endpoint. This would provide far higher transmission speeds while leaving the CPU to do nothing but rendering the image.
After this is implemented, the scrolling might be further optimized by using DMA instead of CPU driven memory moves, expanding the commands to draw other shapes and providing a hook for tearing free rendering using VSYNC.
What is currently far outside of the scope but definitely for consideration in the future is a sprite system. This would move this project from a simple GPU that supports text and some basic shapes to a full graphics engine that could render more sophisticated interfaces and even basic games.
